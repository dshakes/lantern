Pause snapshots the VM's memory and disk and frees its concurrency slot. Resume loads the snapshot back into the same `vm_id`. Fork loads it into several new VMs at once. A running VM also suspends itself when idle and wakes on the next request.

## Idle suspend

Set `idleTimeoutSecs` on the schedule request (`--idle-timeout N` on the CLI; `0` or unset means never). When a sandbox sees no exec, tool call or file request for that long, it is snapshotted and its compute and quota slot released. The scheduler sweeps every 10 s on activity reported with the 30 s node heartbeat, so suspension can trail the timeout by up to about 40 s. The next exec or file request (REST, CLI or SDK) resumes it transparently: the caller sees a slower first response (about 4 s for the in-guest exec channel to re-establish), not an error. A VM paused by an operator (`POST /pause`) is never auto-resumed.

The snapshot stays in storage while suspended. Lifecycle latency numbers (Lima nested-virt, Apple M4 Max, aarch64, indicative, not bare metal) are in `docs/benchmarks/runtime-latency.md`.

## Forks

Forks share the parent snapshot's memory copy-on-write, so N forks cost one snapshot's memory plus whatever each child writes. Each fork gets its own private copy of the captured disk. The per-call cap defaults to 100 and is set with `PAL_MAX_FORK_COUNT` (ceiling 1000).

## Snapshots

A snapshot captures the VM's guest memory, its vmstate and its writable disk. The disk is copied while the VM is paused for the memory snapshot, so memory and disk describe the same instant (a restored guest's page cache matches the disk underneath it). Every snapshot is stored as three artifacts:

- `snapshot`: Firecracker vmstate.
- `mem`: guest memory (as large as the VM's RAM).
- `rootfs`: the captured disk.

Restore and fork stage from the captured disk. Resume, idle wake and each fork copy the snapshot's `rootfs` to a per-VM writable path (or into the jail), so files written before the snapshot are still there and writes after it stay private to that VM. A legacy snapshot taken before disks were captured has no `rootfs`; it restores onto the base image, which does not match its memory, so re-snapshot long-lived VMs.

### Where snapshots are stored

The runtime-manager's snapshot store keeps the canonical copy on local disk and optionally mirrors it to S3/MinIO. All reads go through the local tier and fall back to S3 when the local copy is gone.

| Env var (runtime-manager) | Default | Purpose |
| --- | --- | --- |
| `SNAPSHOT_DIR` | `/var/lib/pal/snapshots` | Local tier root, laid out `<agent_version_id>/<vm_id>/<snapshot_id>/` |
| `S3_ENDPOINT` + `S3_BUCKET` | unset (S3 tier off) | Enable the S3/MinIO mirror under `snapshots/<agent_version_id>/<vm_id>/<snapshot_id>/` |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | unset | S3 credentials (same variables the control-plane uses) |

An S3 upload failure is logged and does not fail the snapshot; the local copy is already safe. Retention is applied after every write: the newest 3 snapshots per VM are kept and anything older than 7 days is deleted.

### Cost

Each snapshot stores `mem` (up to the VM's RAM) plus a full copy of the disk, and every restore or fork copies the disk again. Disk capture happens while the VM is paused, so it adds to pause time (the copy reflinks on XFS/btrfs and byte-copies elsewhere). On the jailed path forks share the memory file via a hard link, so only the disk is copied per fork.

Indicative numbers from [`docs/benchmarks/runtime-latency.md`](repo:/blob/master/docs/benchmarks/runtime-latency.md) (run 2026-10-27), measured in a Lima nested-virt guest on an Apple M4 Max (aarch64, 1 vCPU, 128 MiB VM, jailed). Dev laptop, nested virtualization: preliminary, not production numbers. (Firecracker's own ~125 ms bare-metal cold boot is a published figure, not our measurement.)

| Step | Indicative |
| --- | --- |
| Memory snapshot (128 MiB, 134 MB written; measured before disk capture) | 634 ms |
| Restore (Spawn RPC) | 138 ms |
| Fork spawn (hard-linked memory plus per-VM rootfs copy) | 131 / 145 / 160 ms |
| First exec after restore (p50 of 5 runs) | 2,857 ms |
| Stop | about 200 ms |

The snapshot row predates disk capture, so add the `rootfs` copy (reflinked on XFS/btrfs, a full copy elsewhere) to snapshot time. The benchmark doc estimates the per-VM rootfs copy at about 5 to 50 ms for a 20 to 100 MiB image.

After a restore the runtime-manager holds the first exec until the restored harness has re-identified and sent its first heartbeat (`PAL_HARNESS_READY_TIMEOUT_MS`, default 5 s), so a caller makes one call instead of retrying. On Lima that first exec lands in 2.6 to 3.1 s, almost all of it slow CPU-bound guest work under nested virtualization; bare-metal KVM has not been measured.

## REST

```
# Pause: snapshot + stop. Frees the quota slot.
POST /v1/runtime/vms/{id}/pause
→ { "vmId": "...", "snapshotId": "...", "state": "paused" }

# Resume: same vm id. 402 if quota is exhausted, 409 if the VM is not paused.
POST /v1/runtime/vms/{id}/resume
→ { "vmId": "...", "snapshotId": "...", "state": "running" }

# Fork: count 1..100 by default (PAL_MAX_FORK_COUNT, ceiling 1000); forks share the snapshot memory copy-on-write. Each fork gets its own vm_id, cert and agent identity.
POST /v1/runtime/vms/{id}/fork
{ "count": 3 }
→ { "sourceVmId": "...", "snapshotId": "...",
    "forks": [ { "vmId": "...", "state": "running" },
               { "vmId": "...", "state": "failed", "error": "..." } ] }
```

`GET /v1/runtime/vms/{id}` additionally returns `snapshotId` and `parentVmId` (set on forks), and `state` may be `paused`. Restoring a snapshot onto a fresh TAP (resume, idle wake, fork; not broker mode) uses snapshot-load `network_overrides`, which needs Firecracker 1.12 or later with the jailer (tested on 1.15).

Snapshots are owned by the tenant that created them; restoring another tenant's snapshot returns `NOT_FOUND` (ADR 0025). A restored VM re-identifies with a fresh identity rather than reusing the source VM's.

## Streaming exec

`POST /v1/runtime/vms/{id}/exec` buffers output by default. Send `Accept: text/event-stream` to receive `stdout`, `stderr`, then `exit` events (or `error`) as they happen. Exec is execve-style: `command` is the executable, `argv` its arguments. Pass `/bin/sh` with `["-c", …]` for a shell line.

## Files

Read and write files under the VM's `/workspace`. These run through the in-guest harness tool runner, so paths are confined to `/workspace` (escapes return 400) and files are accessed as the workload user. Content is UTF-8 text, at most 1 MiB (writes above return 413; larger reads are cut and flagged with `X-Pal-Truncated: true`). Firecracker VMs only; other backends return 503.

```
GET /v1/runtime/vms/{id}/files?path=src            # → { path, entries: [{name, type, size}], truncated }
GET /v1/runtime/vms/{id}/files/content?path=a.txt  # → raw text
PUT /v1/runtime/vms/{id}/files/content?path=a.txt  # body = file bytes → { path, bytesWritten }
```

## SDKs

The Go SDK exposes `PauseVM`, `ResumeVM`, `ForkVM`, `ListFiles`, `ReadFile` and `WriteFile`.

```ts
const { snapshotId } = await client.runtime.pause(vmId);
await client.runtime.resume(vmId);                        // same vm id
const { forks } = await client.runtime.fork(vmId, { count: 3 });
for (const f of forks) if (f.error) console.warn(f.vmId, f.error);

await client.runtime.writeFile(vmId, "job.py", "print('hi')");
const { content } = await client.runtime.readFile(vmId, "job.py");
const { entries } = await client.runtime.listFiles(vmId);

for await (const ev of client.runtime.execStream(vmId, {
  command: "/bin/sh",
  argv: ["-c", "pip install -q requests && python job.py"],
})) {
  if (ev.type === "exit") console.log("exit", ev.exitCode);
  else process.stdout.write(ev.data);                     // stdout | stderr
}
```

await client.runtime.pause(vm_id)
await client.runtime.resume(vm_id)
result = await client.runtime.fork(vm_id, count=3)
for f in result.forks:
    if f.error:
        print(f.vm_id, f.error)

await client.runtime.write_file(vm_id, "job.py", "print('hi')")
text = (await client.runtime.read_file(vm_id, "job.py"))["content"]

async for ev in client.runtime.exec_stream(vm_id, "/bin/sh", ["-c", "python job.py"]):

        print(ev.data, end="")
