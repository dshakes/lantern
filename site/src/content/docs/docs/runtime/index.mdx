Every run executes in one of two tiers: **shared** (the inline executor inside the control-plane) or **microVM** (the W12 Kubernetes/Firecracker/Kata stack). The tier is declared in the agent version's `manifest.isolation` at publish time. The caller cannot override it.

The one decision you make is trust. Agents running code you wrote go in the shared tier. Agents running code you don't fully trust (user uploads, arbitrary shell commands, packages from the internet) go in the microVM tier, where each run gets its own disposable virtual machine. Crash recovery, live streaming and receipts work the same in both tiers.

## Two tiers, one journal

Every step of every run is written to the journal before it executes, in one place, regardless of tier. That is what makes crash recovery, the dashboard waterfall and signed receipts possible. Both tiers write to the same `journal_events` table. The run waterfall, Ed25519 receipts and crash replay are tier-agnostic. There is no second event store.

| | Shared tier | MicroVM tier |
| --- | --- | --- |
| Declared as | `"shared"` (default, or absent) | `"microvm"` |
| Executor | Goroutine inside control-plane (`executeRunInlineSync`) | Scheduler, then manager, then Firecracker / Kata / K8s Job |
| Isolation | Same OS process. First-party code only | Firecracker or Kata microVM, or a gVisor / K8s Job pod (see [Isolation classes](/docs/runtime/isolation/)) |
| Egress | Not sandboxed (first-party code) | Per-VM allowlist, deny by default. Default mode: in-guest proxy plus iptables REDIRECT (required in prod). Opt-in broker mode (Firecracker only): no NIC, host-side allowlist over vsock |
| Crash resume | Recovery sweep (default 30 s) plus completed-step journal replay | Recovery sweep re-schedules the VM; gives up after 3 attempts |
| Secret delivery | Resolved inline at step time, never logged | Default: short-TTL values vended to the workload over a peer-authenticated socket. Broker mode: credentials injected on the host, never enter the VM |
| Use case | Loop agents, bridge replies, dashboard runs, trusted workflows | User-supplied code, exec tools, untrusted packages |
| Downgrade safety | N/A | Never falls back to shared. Failure is explicit (`microvm_unavailable`) |

## How routing works

When `POST /v1/runs` arrives, the control-plane reads `manifest.isolation` from the resolved agent version and dispatches to either `executeRunInline` (shared) or `scheduleAgentSpec` (microVM). The caller supplies only the input. The tier comes from the manifest.

Unknown values in `manifest.isolation` are rejected at agent-version publish time with HTTP 400, so a typo fails at deploy, not at run time.

<Aside type="caution" title="No silent downgrade">
If the microVM tier is unavailable (scheduler unreachable, quota exceeded, manager down), the run fails with code `microvm_unavailable`. A VM that exits unexpectedly produces `microvm_exit`; exhausting the 3-attempt resume limit produces `microvm_resume_exhausted`. None of these ever fall back to the shared tier. The isolation declaration is a security boundary.
</Aside>

## Shared tier

The shared tier is a goroutine inside the control-plane. Most runs execute here: loop agents, bridge replies, dashboard runs, cron-triggered runs and sessions. It drives either the plain-LLM tool-use loop (for agents with no `workflow` JSONB) or the workflow interpreter (for agents with a graph saved in the visual editor). Crash-resume is handled by the recovery sweep. See [Durable execution](/docs/runtime/durable-execution/).

Entry points: `POST /v1/runs`, `POST /v1/sessions/{id}/messages`, the cron scheduler, the loop agent tick, and bridge-triggered runs.

## MicroVM tier

The microVM tier is required for agents that run user-supplied code, exec arbitrary tools, or load untrusted packages. Declare it in the manifest:

```yaml
manifest:
  isolation: microvm          # routes this agent version to the W12 stack
  image_digest: …@sha256:…
  limits: { vcpu: "250m", memory: "128Mi", timeout: "60s" }
  egress_rules: [{ host: "api.openai.com" }]
  idempotent: true
```

The in-guest tool runner gives the harness a typed tool registry: `shell_exec`, `http_fetch`, `read_file`, `write_file` and `list_dir`. File tools are confined to `/workspace`. Workflow-graph agents reach it through the engine's `tool_call` step.

## Service-health sweep

A background loop TCP-probes peer services every 60 s (`PAL_HEALTH_SWEEP_INTERVAL`). After 3 consecutive failures it declares the peer DOWN and sends a message to the operator's notification channel, once on transition, so there are no alert storms. Read the current snapshot:

```
GET /v1/system/health   # JWT-authed
```

```json
{
  "services": [
    {
      "name": "runtime-manager",
      "addr": "localhost:50054",
      "up": false,
      "consecutiveFailures": 5,
      "lastChecked": "2026-07-23T10:00:00Z"
    }
  ]
}
```

## Operating it in production

Four things an operator cares about: work is never lost (checkpointing), crashed work restarts itself (recovery), a runaway tenant can't take the platform down (throttling), and you can see all of it (monitoring). The knobs are environment variables; the views are REST, the CLI and the dashboard.

| Capability | Mechanism | Knobs / views |
| --- | --- | --- |
| Checkpointing | Every step journaled to `journal_events` before it runs (both tiers). Firecracker VM snapshots persisted to S3 (ADR 0007) | [Durable execution](/docs/runtime/durable-execution/) |
| Auto-restart | Recovery sweep steals expired run leases and re-drives from the last completed step. microVM runs re-scheduled with `PAL_RESUME=1`, at most 3 attempts. Scheduler is HA via leader election | `PAL_RECOVERY_INTERVAL` (default 30 s) |
| Throttling | Budget gate blocks over-budget runs with 402. Per-tenant concurrent-VM hard cap (gRPC `ResourceExhausted`). Spawn-storm guard returns 429. Per-step timeout | `PAL_SPAWN_RATE_PER_MIN` (default 120), `PAL_SPAWN_BURST`, [Budgets](/docs/build/budgets/) |
| Job monitoring | VM list / detail / audit trail / live SSE logs / per-VM metrics / cluster and quota views | `GET /v1/runtime/vms`, `/v1/runtime/metrics`, `/v1/runtime/cluster`, `/v1/runtime/audit`, `pal vm list\|get\|logs\|stop\|exec`, dashboard `/runtime` |
| Telemetry | Five `lantern.run.*` OTel metrics. Scheduler Prometheus scrape. Prometheus alert rules and Grafana dashboards in `infra/monitoring/`, runbooks in `docs/runbooks/` | scheduler `:8085/metrics`, [Observability](/docs/observability/) |
| Traceability | W3C trace context propagated control-plane, scheduler, manager and in-VM harness. One correlated identity chain (tenant, run, step, instance). Ed25519 receipts | [Receipts](/docs/security/receipts/), [Observability](/docs/observability/) |

## System architecture

For the technical view of how the control-plane, scheduler, runtime-manager and in-VM harness collaborate across both tiers on the same `journal_events` substrate, see [Architecture](/docs/runtime/architecture/).

## What makes it different

- **Durable by default.** Every step is journaled. A crash-replay skips completed nodes and replays cached LLM outputs, so there are no re-spent tokens and no double side-effects.
- **Isolation by manifest.** Isolation strength is declared in the agent version, not chosen by the caller. Fail-closed: untrusted workloads are refused without the hardened RuntimeClass, never silently downgraded.
- **One observability contract.** One OTel trace per spawn, W3C `traceparent` end-to-end, five `lantern.run.*` metrics, and a shared span-attribute contract from HTTP entry to harness exit.
