Every run executes in one of two tiers: **shared** (the inline executor inside the control plane) or **microVM** (the scheduler, runtime-manager and Firecracker/Kata stack). The tier is declared in the agent version's `manifest.isolation` at publish time.

Code you wrote goes in the shared tier. User uploads, arbitrary shell commands and internet packages go in the microVM tier. Crash recovery, streaming and receipts work the same in both.

## Two tiers, one journal

Every step is written to the `journal_events` table before it executes, in both tiers. Crash recovery, the dashboard waterfall and Ed25519 receipts all read that one table; there is no second event store.

| | Shared tier | MicroVM tier |
| --- | --- | --- |
| Declared as | `"shared"` (default, or absent) | `"microvm"` |
| Executor | Goroutine inside control-plane (`executeRunInlineSync`) | Scheduler, then manager, then Firecracker / Kata / K8s Job |
| Isolation | Same OS process. First-party code only | Firecracker or Kata microVM, or a gVisor / K8s Job pod (see [Isolation classes](/docs/runtime/isolation/)) |
| Egress | Not sandboxed (first-party code) | Per-VM allowlist, deny by default. Default mode: in-guest proxy plus iptables REDIRECT (required in prod). Opt-in broker mode (Firecracker only): no NIC, host-side allowlist over vsock |
| Crash resume | Recovery sweep (default 30 s) plus completed-step journal replay | Recovery sweep re-schedules the VM; gives up after 3 attempts |
| Secret delivery | Resolved inline at step time, never logged | Default: short-TTL values vended to the workload over a peer-authenticated socket. Broker mode: credentials injected on the host, never enter the VM |
| Use case | Loop agents, bridge replies, dashboard runs, trusted workflows | User-supplied code, exec tools, untrusted packages |
| Downgrade safety | N/A | Never falls back to shared. Failure is explicit (`microvm_unavailable`) |

## How routing works

`POST /v1/runs` reads `manifest.isolation` from the resolved agent version and dispatches to `executeRunInline` (shared) or `scheduleAgentSpec` (microVM). The caller supplies only the input. An unknown `isolation` value is rejected at publish with HTTP 400, so a typo fails at deploy.

<Aside type="caution" title="No silent downgrade">
If the microVM tier is unavailable (scheduler unreachable, quota exceeded, manager down), the run fails with code `microvm_unavailable`. A VM that exits unexpectedly produces `microvm_exit`; exhausting the 3-attempt resume limit produces `microvm_resume_exhausted`. None of these ever fall back to the shared tier. The isolation declaration is a security boundary.
</Aside>

## Shared tier

A goroutine inside the control plane runs most work: dashboard runs, cron runs, sessions and bridge replies. It drives the plain-LLM tool-use loop, or the workflow interpreter for agents with a saved graph. Crash-resume is covered in [Durable execution](/docs/runtime/durable-execution/).

## MicroVM tier

Declare it in the manifest:

```yaml
manifest:
  isolation: microvm          # routes this agent version to the microVM stack
  image_digest: …@sha256:…
  limits: { vcpu: "250m", memory: "128Mi", timeout: "60s" }
  egress_rules: [{ pattern: "api.openai.com" }]
  idempotent: true
```

`isolation: microvm` selects the microVM tier and schedules the workload with isolation class `standard`. To choose a stronger class (`untrusted`, `hostile`, `wasm`), schedule a headless agent with `pal run agent.yaml`; see [Isolation classes](/docs/runtime/isolation/).

The in-guest tool runner gives the harness a typed tool registry: `shell_exec`, `http_fetch`, `read_file`, `write_file` and `list_dir`. File tools are confined to `/workspace`. Workflow-graph agents reach it through the engine's `tool_call` step.

## Service-health sweep

A background loop TCP-probes peer services every 60 s (`PAL_HEALTH_SWEEP_INTERVAL`). After 3 consecutive failures it marks the peer DOWN and notifies the operator once per transition. Current snapshot:

```
GET /v1/system/health   # JWT-authed
```

```json
{
  "services": [
    {
      "name": "runtime-manager",
      "addr": "localhost:50054",
      "up": false,
      "consecutiveFailures": 5,
      "lastChecked": "2026-07-23T10:00:00Z"
    }
  ]
}
```

## Operating it in production

Checkpointing, auto-restart, throttling and monitoring, with environment-variable knobs and REST, CLI and dashboard views.

| Capability | Mechanism | Knobs / views |
| --- | --- | --- |
| Checkpointing | Every step journaled to `journal_events` before it runs (both tiers). Firecracker VM snapshots kept on the node and optionally mirrored to S3 (ADR 0007) | [Durable execution](/docs/runtime/durable-execution/) |
| Auto-restart | Recovery sweep steals expired run leases and re-drives from the last completed step. microVM runs re-scheduled with `PAL_RESUME=1` (`PAL_RESUME=1` is accepted as an alias), at most 3 attempts. Scheduler is HA via leader election | `PAL_RECOVERY_INTERVAL` (default 30 s) |
| Throttling | Budget gate blocks over-budget runs with 402. Per-tenant concurrent-VM hard cap (gRPC `ResourceExhausted`). Spawn-storm guard returns 429. Per-step timeout | `PAL_SPAWN_RATE_PER_MIN` (default 120), `PAL_SPAWN_BURST`, [Budgets](/docs/build/budgets/) |
| Job monitoring | VM list / detail / audit trail / live SSE logs / per-VM metrics / cluster and quota views | `GET /v1/runtime/vms`, `/v1/runtime/metrics`, `/v1/runtime/cluster`, `/v1/runtime/audit`, `pal vm list\|get\|logs\|stop\|exec`, dashboard `/runtime` |
| Backend | One per runtime-manager process, `RUNTIME_BACKEND` = `k8s` (default), `firecracker`, `kata`, `docker`, `wasm` | `RUNTIME_BACKEND` |
| Telemetry | Five `pal.run.*` OTel metrics. Scheduler Prometheus scrape. Prometheus alert rules and Grafana dashboards in `infra/monitoring/`, runbooks in `docs/runbooks/` | scheduler `:8085/metrics`, [Observability](/docs/observability/) |
| Traceability | W3C trace context propagated control-plane, scheduler, manager and in-VM harness. One correlated identity chain (tenant, run, step, instance). Ed25519 receipts | [Receipts](/docs/security/receipts/), [Observability](/docs/observability/) |

Interactive multi-turn agents use sessions, which run on the shared tier ([Agents](/docs/build/agents/)). For how the control plane, scheduler, manager and harness collaborate, see [Runtime internals](/docs/runtime/architecture/).
