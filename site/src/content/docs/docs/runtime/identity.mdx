Every headless agent spawn gets its own cryptographic identity, and secrets are vended to it at execution time over a mutually-authenticated channel, never baked into the image or the spec. The two are linked: the per-instance identity is what authenticates the secret-vending call.

Agents need API keys to do their jobs, and API keys are what an attacker wants. PAL Runtime never puts the real key anywhere the agent's code can casually find it. The agent config holds only a reference (a name, not a value). The actual key is handed over at the last possible moment, expires quickly, and is delivered only to a process that can cryptographically prove it is the agent it claims to be. Each spawn also gets its own identity, so anything it does can be traced back to exactly that one run.

## Per-instance Ed25519 identity

At spawn, the runtime issues the instance its own Ed25519 keypair. The identity is scoped to that single spawn (two runs of the same agent have different keys) and it is what the observability layer uses as `agent_instance_id` to keep traces from colliding.

### Externally verifiable

The instance's public identity is verifiable at a well-known endpoint, so a downstream service can confirm it is talking to a genuine PAL Runtime-issued instance:

```
GET /.well-known/lantern-agent-identity
```

## Short-TTL secret vending

The workload never ships with secrets. Instead it requests them at runtime via the harness's secrets socket (`/run/lantern/secrets.sock`), which authenticates every connecting peer with `SO_PEERCRED` (kernel-attested uid and pid, not spoofable). The harness only vends to the workload uid injected by the manager as `PAL_WORKLOAD_UID`. Secrets have a 300-second TTL.

The control-plane resolves `lantern.secret/...` references through a relay endpoint protected by a pre-shared `X-Lantern-Runtime-Token` header (SHA-256 compared, set via `PAL_RUNTIME_SECRET_TOKEN`; the endpoint returns 403 when unset).

<Aside type="caution">
mTLS between the runtime-manager and control-plane is the planned stronger follow-up and is not yet implemented.
</Aside>

- **`SO_PEERCRED` peer auth.** The kernel attests uid/pid on every socket connection; there is no credential the workload can forge.
- **Short TTL (300 s).** A leaked value has a small blast radius; the workload re-requests as needed.
- **Pre-shared token on the relay.** The manager authenticates to the control-plane relay via `X-Lantern-Runtime-Token`; fail-closed when unset.

## The `lantern.secret/...` ref form

In the spec you reference a secret, you do not embed it. The runtime resolves the reference at execution time, so the raw value never appears in the image, logs, traces or run state. From demo 02:

```yaml
secrets:
  - env_name: USER_AGENT
    secret_uri: lantern.secret://__tenant__/key/scraper-user-agent
```

The `lantern.secret/...` ref form is the same convention used across the platform (see [Security](/docs/runtime/security/)). The runtime is where it is resolved, inside the isolation boundary, at the moment the workload needs it.

<Aside type="caution">
Pair secret vending with the right [isolation class](/docs/runtime/isolation/). A workload that loads internet packages and also holds a secret should be `untrusted` with an egress allowlist, so a compromised dependency can't exfiltrate the vended value to an arbitrary host.
</Aside>

## Broker mode: credentials never enter the VM

Vending still puts a short-lived value inside the VM, so a compromised workload can read it while it is valid. The opt-in broker mode (`PAL_EGRESS_MODE=broker`, Firecracker only) closes that gap for outbound API calls: the VM has no network device, and the host broker resolves the `lantern.secret` ref and injects the header on the way out. The workload never holds the value. See [Egress and credentials](/docs/runtime/egress/).

## What you get

- Per-spawn Ed25519 identity, externally verifiable at `/.well-known/lantern-agent-identity`.
- `SO_PEERCRED` peer auth and short-TTL secret vending via the harness Unix socket.
- Reference-form secrets resolved inside the isolation boundary. Raw values never touch the image, env, logs or run state.

## Operating notes

- **The manager never holds the decryption key.** `PAL_CREDENTIAL_KEY` lives only on the control plane, which resolves a `lantern.secret/` ref over `POST /v1/runtime/secrets/resolve`. A compromised manager node cannot decrypt a tenant's secrets on its own.
- **The relay is fail-closed.** It needs the pre-shared `PAL_RUNTIME_SECRET_TOKEN` on both the control plane and the manager (unset on the control plane: 403), and is not reachable with an end-user JWT.
- **Per-VM mTLS.** The manager binds the `vm_id` reported on a vend to the mTLS peer certificate, so a workload cannot claim to be another VM. When the VM terminates its instance token stops working.
- **Dev stub.** Without a manager, the harness reads secrets from its own environment when `PAL_ALLOW_SECRET_STUB=1`. Never set it in production.
- **Credential encryption.** Provider keys and connector tokens are AES-256-GCM encrypted at rest with `PAL_CREDENTIAL_KEY`; the control plane refuses to start in production without it. See [Environment variables](/docs/reference/env-vars/).
