An *agent* is an AI worker with a name and instructions. A *run* is one execution: input in, output out. The *event stream* is the live record of a run.

<Aside type="tip" title="No API key yet?">
`make demo` needs only Docker and answers from recorded replays. See [Demo mode](/docs/start/demo/). This page runs your own agent against your own key.
</Aside>

## Before you start

- A running stack: `pal dev` ([Installation](/docs/start/installation/) if you have not set it up).
- An OpenAI or Anthropic key. You can add it during onboarding.
- Optional, for the terminal path: the CLI, built with `( cd packages/cli && go build -o "$(go env GOPATH)/bin/pal" ./cmd/pal )`. `pal doctor` checks the stack, including whether the sandbox runtime is wired.

## In the dashboard

Open [localhost:3001/onboarding](http://localhost:3001/onboarding) and sign in (the seeded dev account: `admin@pal.local` / `pal`). It is a conversation with PAL's onboarding agent, with a progress rail beside it (a one-line summary on a phone).

Say what you want in your own words. The agent asks follow-ups, decides the next step and does it with real calls:

<Steps>

1. **Model key.** With no key yet, the agent's first job is to get one: a secure form saves it and makes a real test call. The key never appears in the conversation; one pasted into the chat by mistake is saved, tested and removed before anything is stored.

2. **Describe the goal**, for example *"Turn my rough meeting notes into a short summary with action items."* The agent designs an agent (name, instructions, a capability model such as `auto`, never a vendor name, and a first task) and shows it. Ask for changes in plain words, or approve.

3. **Create and run.** On your go-ahead it creates the agent, reads it back, runs it once and shows the real output, or the real error and what to do about it.

</Steps>

The agent can only call the tools the current step allows; anything else is refused and said so in the chat. It never reports success a call did not return. If it can't reach the model, the page switches to the **step-by-step** setup and says why; **Step by step** in the header opens it any time, with the same saved progress (starters, spec editing and the optional sandbox run live there).

Progress is stored on the server, so a reload or another browser resumes where you left off; **Start over** clears it. When a step fails, the page names the cause and offers one fix:

| What you see | One-click fix |
| --- | --- |
| No model key configured | Add a model key (the design is retried) |
| Provider rejected the key | Replace the key |
| Design came back unusable | Rephrase the goal, or use the basic design |
| An agent with that name exists | Rename the agent |
| Budget or quota blocked the run | Open budgets |

<Aside type="caution" title="Email verification">
Where verification is required ([Accounts](/docs/build/accounts/)), creating a run before you verify returns `403` with `code: "email_unverified"`. Onboarding shows **Resend verification email** and **I've verified, try again** instead of failing silently.
</Aside>

## In the terminal

```bash
pal onboard
```

On a terminal this is the same conversation as the dashboard: type in your own words; keys go into a hidden prompt, never the chat. `--steps` keeps the step-by-step wizard (health, sign-in, key test, goal, proposal, create, streamed first run), which also takes over if the agent can't reach the model. For CI, `--yes` never prompts and fails at the first broken step:

```bash
pal onboard --yes \
  --provider anthropic --api-key "$ANTHROPIC_API_KEY" \
  --description "Summarize support tickets into one-line triage notes"
```

Other `pal` commands reuse the credentials `pal onboard` saves. To sign in separately: `pal login --email admin@pal.local --password pal`.

## Under the hood

The conversation itself is `POST /v1/onboarding/agent/turn` (`{product: "runtime"|"pal", message?, event?, results?}`); every tool the agent calls is one of the endpoints below. Both paths use public endpoints you can script:

```bash
export PAL_TOKEN=$(curl -s -X POST http://localhost:8080/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@pal.local","password":"pal"}' | jq -r .token)
H="Authorization: Bearer $PAL_TOKEN"; J="Content-Type: application/json"

# 1. Provider key + a real test call
curl -s -X POST localhost:8080/v1/settings/llm-providers -H "$H" -H "$J" \
  -d '{"provider":"anthropic","apiKey":"sk-ant-..."}'
curl -s -X POST localhost:8080/v1/settings/llm-providers/anthropic/test -H "$H"

# 2. Design an agent from a goal (returns the spec: name, systemPrompt, firstInput, rationale, steps)
curl -s -X POST localhost:8080/v1/agents/generate-spec -H "$H" -H "$J" \
  -d '{"description":"Turn meeting notes into action items"}' | tee spec.json

# 3. Create it (the instruction field is systemPrompt)
jq '{name, description, systemPrompt}' spec.json | \
  curl -s -X POST localhost:8080/v1/agents -H "$H" -H "$J" -d @-

# 4. Run it with the suggested first task, then stream events (named SSE events)
RUN_ID=$(jq --argjson i "$(jq .firstInput spec.json)" -n \
  "{agentName: \"$(jq -r .name spec.json)\", input: \$i}" | \
  curl -s -X POST localhost:8080/v1/runs -H "$H" -H "$J" -d @- | jq -r .id)
curl -N localhost:8080/v1/runs/$RUN_ID/events -H "$H" -H "Accept: text/event-stream"
```

`generate-spec` returns `400 {"code":"no_provider"}` with no key, and `502` (`bad_spec` or `llm_failed`) when the model call fails. The event stream closes at `succeeded`, `failed` or `cancelled`; read the final output from `GET /v1/runs/{id}`. Onboarding progress lives at `GET/PUT/DELETE /v1/onboarding`.
