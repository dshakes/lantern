There are two separate deploys. **`pal deploy`** ships an agent to a running control plane, in seconds, as often as you change the agent. **Helm or Terraform** puts the platform in your cloud, once, so agent data stays in your account.

<Diagram name="your-cloud" alt="The control plane runs anywhere. The data plane runs in your VPC and dials out to the control plane, so you open no inbound ports." />

<Aside type="note" title="No hosted cloud yet">
A fully managed PAL cloud is the intended offering, not a shipped one. Today you run the control plane yourself; everything below targets your own cluster.
</Aside>

## Ship an agent

From the agent's directory, against any control plane you are signed in to:

```bash
pal deploy --dry-run   # one read-only lookup: reports "create" or "update", changes nothing
pal deploy --json
```

`pal deploy` reads `agent.yaml` (`name`, `description`, `model`, `system_prompt`, `labels`, `workflow`), creates or updates the agent, saves the workflow graph, then calls `POST /v1/agents/{name}/deploy`. The response carries `"status": "live"` and the agent's invoke URL.

| Exit code | Meaning |
| --- | --- |
| `3` | Unauthorized |
| `4` | Quota or budget (`402`) |
| `5` | Not found |
| `6` | Server error |

## Put the platform in your cloud

<Tabs>
<TabItem label="Helm (one cluster)">

<Steps>

1. Supply the secrets the chart cannot create: `secrets.jwtSecret`, `credentialKey`, `receiptSecret`, `grpcServiceToken`, `schedulerNodeToken`, `appDbPassword`, plus the control plane's gRPC TLS cert and the runtime-manager mTLS client cert.

2. Install with the production values. The chart sets `PAL_ENV=production`, so every production startup guard is on, and a missing secret stops the pod with its name in the log. This all-in-one chart suits simple self-hosted setups; split deployments use `infra/helm/pal-control-plane` and `pal-data-plane`.

   ```bash
   helm dependency build ./infra/helm/pal     # Redis subchart
   helm install pal ./infra/helm/pal --namespace pal --create-namespace \
     --values infra/helm/pal/values-prod.yaml \
     --set secrets.jwtSecret="$JWT_SECRET" --set secrets.credentialKey="$CREDENTIAL_KEY" \
     --set secrets.receiptSecret="$RECEIPT_SECRET" --set secrets.grpcServiceToken="$GRPC_SERVICE_TOKEN" \
     --set secrets.schedulerNodeToken="$SCHEDULER_NODE_TOKEN" --set secrets.appDbPassword="$APP_DB_PASSWORD"
   ```

3. Point the CLI at it. Set `PAL_API_URL` and `PAL_USE_REST=1` to make this permanent. Without `--rest`, `--api-url` is a gRPC address.

   ```bash
   pal --rest --api-url https://<your-host> login
   ```

</Steps>

</TabItem>
<TabItem label="Terraform (data plane per cloud)">

Generate a data plane for EKS, GKE or AKS. Agents then execute in that cloud while the control plane schedules them. `pal infra install` only writes Terraform; you apply it.

```bash
pal infra install --cloud aws --region us-east-1 --node-count 3 --firecracker   # writes ./lantern-data-plane-aws
export TF_VAR_agent_token="<one-time token from Deployments, Register data plane>"
cd lantern-data-plane-aws && terraform init && terraform plan && terraform apply
```

The data plane dials **out** to the control plane (`:50051`) with a one-time bootstrap token, so you open no inbound ports. Register it under **Deployments, Register data plane** or with `POST /v1/data-planes`. `pal infra status` is a placeholder today; check the data-plane-agent pod logs instead.

</TabItem>
</Tabs>

## Which topology

| Topology | Control plane | Data plane | When |
| --- | --- | --- | --- |
| Hybrid (recommended) | One place | Each workload's cloud | Production; agent data stays in your VPC |
| Fully self-hosted | Your cluster | Your cluster | Full control; you run Postgres, Redis and Kubernetes |
| Fully managed | Not offered | Not offered | Not available yet |

Production settings, NetworkPolicy, backups and migrations: [Production deployment](/docs/operate/deployment/). Every variable a production process requires: [Environment variables](/docs/reference/env-vars/#production-checklist). Shape of the split: [Deployment topology](/docs/architecture/deployment-topology/).
