## It brings you what matters. It waits on what is risky.

pal runs on your Mac next to iMessage and WhatsApp. Ordinary replies go out in your voice, paced like you. <p class="kicker">PAL Runtime · for builders</p>

## The parts every production agent needs.

pal is built on PAL Runtime, and your agents get the same platform. Every step is **journaled**, so a crash resumes instead of restarting. Budgets are checked **before** the model is called, so a hard cap costs nothing. Untrusted code runs in a **microVM** with an egress allowlist, and models are addressed by capability, not by vendor name.

## From a checkout to a first result.

Every path starts from a checkout. [Install](/docs/start/installation/) lists the prerequisites (Docker, Node.js 22, Go 1.26).

```sh
git clone https://github.com/dshakes/pal.git && cd pal
(cd packages/cli && go build -o "$(go env GOPATH)/bin/pal" ./cmd/pal)
```

<TabItem label="Use pal">

Install and pair the two channel bridges first ([BOT-SETUP.md](repo:/blob/master/docs/personal/BOT-SETUP.md)). Then `pal setup` walks you through the rest and checks each channel live. This is a real run on a Mac where neither bridge was started yet, so step 2 says how to fix it; lines in `<…>` come from your model.

```console
$ pal dev            # the control plane and dashboard, on this Mac
$ pal setup
pal setup
────────────────────────────────────────────────

1. Meet pal
   <pal introduces itself and says what it will touch>
   Any questions first? (Enter to continue) >
   pal may read your iMessage/WhatsApp on this Mac and reply as you, sending conversation text to your own model provider. Agree? [y/N] y
   Optional: learn your voice from messages you've sent (read once, not stored)? [y/N] y
2. Connect channels (checked live)
   • iMessage: the bridge isn't running — start it (`pal dev`), then re-check
   • WhatsApp: the bridge isn't running — start it (`pal dev`), then re-check
   [i] start iMessage + check permissions  [w] link WhatsApp  [Enter] re-check  [q] quit >
```

With a bridge running, its line reads `✓ iMessage: connected` (or `✓ WhatsApp: connected`) and setup moves on to your voice, trust, your people and facts, and a first Brief. `pal setup` resumes where you left off and never gives consent for you. ## Every number links to its source.

Real Firecracker microVMs, median of 20 runs, from the committed [runtime latency benchmark](repo:/blob/master/docs/benchmarks/runtime-latency.md). They were measured under nested virtualization on a laptop, so compare changes with them; they are not production SLOs.

| Operation | p50 |
| --- | --: |
| Spawn a microVM (RPC returns) | 143 ms |
| Exec round trip in a warm VM | 115 ms |
| Restore a paused VM (RPC returns) | 131 ms |
| Restore, then first exec answered | 2,491 ms |
| Egress request refused by the broker | 32 ms |

How the numbers move a sandbox through pause, resume and fork: [Sandbox lifecycle](/docs/runtime/sandbox-lifecycle/).

## In production, a missing guard stops the service.

The chart sets the environment to `production`. From then on these refuse to start, rather than run without the guard:

| Missing | What refuses |
| --- | --- |
| Shared service token (`PAL_GRPC_SERVICE_TOKEN`) | The control plane, and every internal gRPC service that checks it |
| Encryption key for stored credentials (`PAL_CREDENTIAL_KEY`) | The control plane |
| Restricted database role for row-level security (`PAL_APP_DB_PASSWORD`) | The control plane, unless you opt out with `PAL_RLS_ENFORCE=0` |
| TLS certificate and key (`PAL_TLS_CERT`, `PAL_TLS_KEY`) | The gateway |
| The firewall rule that forces sandbox egress through the allowlist, when egress rules are declared | The workload inside the microVM |

Each boundary and what it demands: [Security model](/docs/security/) and [Security boundaries](/docs/architecture/security-boundaries/).
